SMART EVENT MANAGEMENT SYSTEM
MySQL Project – Questions, SQL Answers, outputs & Reasons
===============================================================

DATABASE TABLES
---------------
1. Venues(venue_id, venue_name, location, capacity)
2. Organizers(organizer_id, organizer_name, contact_email, phone_number)
3. Attendees(attendee_id, name, email, phone_number)
4. Events(event_id, event_name, event_date, venue_id, organizer_id, ticket_price, total_seats, available_seats)
5. Tickets(ticket_id, event_id, attendee_id, booking_date, status)
6. Payments(payment_id, ticket_id, amount_paid, payment_status, payment_date)

Q2. WHERE, HAVING, LIMIT
---------------------------------------------------------------

A. Upcoming events in Surat
SQL:
SELECT e.event_id, e.event_name, e.event_date, v.location
FROM Events e
JOIN Venues v ON e.venue_id = v.venue_id
WHERE e.event_date >= CURDATE() AND v.location = 'Surat'
ORDER BY e.event_date;

output on 24-Oct-2026:
+----------+--------------+------------+----------+
| event_id | event_name   | event_date | location |
+----------+--------------+------------+----------+
|        1 | Tech Summit  | 2026-12-05 | Surat    |
|        4 | Startup Expo | 2026-12-20 | Surat    |
+----------+--------------+------------+----------+
2 rows in set (0.016 sec)

Reason:
WHERE filters future/current events in Surat; ORDER BY sorts them by date.

B. Top 5 events by successful revenue
SQL:
SELECT e.event_name, SUM(p.amount_paid) AS revenue
FROM Events e
JOIN Tickets t ON e.event_id = t.event_id
JOIN Payments p ON t.ticket_id = p.ticket_id
WHERE p.payment_status = 'Success'
GROUP BY e.event_id, e.event_name
ORDER BY revenue DESC
LIMIT 5;

output:
+---------------+---------+
| event_name    | revenue |
+---------------+---------+
| Tech Summit   | 2400.00 |
| Music Night   |  800.00 |
| Data Workshop |  500.00 |
+---------------+---------+
3 rows in set (0.010 sec)

Reason:
Only successful payments count. GROUP BY calculates revenue per event, ORDER BY puts highest first, and LIMIT 5 returns up to five rows. Only three events have successful payments in the sample.

D. Events with more than one ticket record (HAVING)

Q6. PRIMARY KEY AND FOREIGN KEY RELATIONSHIPS
---------------------------------------------------------------

A. Prevent the same attendee booking the same event more than once
Constraint already in the uploaded schema:
CONSTRAINT uq_attendee_event UNIQUE (event_id, attendee_id)

Reason:
The UNIQUE constraint makes each event_id + attendee_id combination unique. An attendee can book different events, but cannot create a second ticket row for the same event.

B. Link payments to valid tickets
Constraint already in the uploaded schema:
CONSTRAINT fk_payment_ticket FOREIGN KEY (ticket_id) REFERENCES Tickets(ticket_id)

Reason:
A payment's ticket_id must exist in Tickets. This prevents a payment from referring to a nonexistent ticket.

B. LEFT JOIN – Ticket holders without successful payment (excluding cancelled tickets)

The LEFT JOIN tries to match a successful payment. If none exists, payment columns are NULL. Cancelled tickets are excluded.
